# 协作规范

状态：已按立项报告对齐
最后更新：2026-10-11

## 三人分工

| 方向 | 主要职责 | 主要文档与代码 |
| --- | --- | --- |
| 项目统筹与算法 | 进度、申报和结项材料；多模态特征、模型与评估 | `docs/`、`ml/`、`research/`、算法服务 |
| 前端 后端与安全 | Web 交互、FastAPI、MySQL、部署和数据安全 | `frontend/`、`backend/`、部署配置 |
| 心理学支持与用户研究 | 理论审查、量表与效果评估、伦理、招募和反馈分析 | 用户研究方案、评估材料、安全测试集 |

具体人员承担的任务以当期里程碑和任务看板为准，跨模块接口必须由双方共同评审。

## 协作流程

1. 开始任务前确认立项范围、验收标准和数据安全要求。
2. 字段、接口、Prompt 或研究流程变化时同步更新契约和测试。
3. 跨成员依赖通过 OpenAPI、JSON Schema、Mock 数据或可执行测试交付。
4. 关键方案在 `decisions/` 新增 ADR，评审后实施。
5. 完成任务后更新实现状态、测试证据和已知局限。

涉及微服务拆分、数据库、认证方式、对象存储协议、任务系统、模块数据所有权或新增真实参与者数据类别的变化，必须先新增 ADR；不得通过普通功能提交隐式改变架构。

## 提交建议

本次重整提交到 `LLM-Study`。后续变更通过工作分支向 `LLM-Study` 提 PR，至少获得一名评审者批准后合并。未经用户明确允许，不向 `main` 提交、合并或推送；不再自动经 `moyi` 发布到 `main`。远端保护是否生效以 GitHub 实际设置为准。

- `docs:` 文档与决策。
- `feat:` 用户可见功能。
- `research:` 数据、Prompt、算法与评估。
- `fix:` 缺陷修复。
- `test:` 测试与安全用例。
- `refactor:` 不改变行为的重构。
