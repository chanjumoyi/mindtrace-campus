- A是笔迹算法与模型工程。
- B是多模态算法与Agent工程。
- C是前端、Java后端、数据库、苍穹集成和部署。

所以问题不在于“AB后端、C前端”，而在于C同时承担了前端、工程后端和平台落地，分工不均衡。

建议调整为下面这种方式。

| 成员 | 核心主责           | 同时负责的工程工作                     |
| ---- | ------------------ | -------------------------------------- |
| A    | 笔迹模型与数据     | 笔迹采集页面、笔迹分析接口             |
| B    | 房树人/沙盘与Agent | 房树人和沙盘页面、对应分析接口         |
| C    | 系统架构与苍穹集成 | 公共页面、Java网关、数据库、权限、部署 |

具体来说：

### A：笔迹功能负责人

负责完整的笔迹模块，而不只是训练模型：

- 笔迹Canvas采集页面。
- 触控笔、鼠标、触摸设备适配。
- 轨迹数据格式和数据质量检查。
- 特征提取和模型训练。
- 笔迹分析推理接口。
- 笔迹结果展示组件。
- 该模块的单元测试和技术文档。

交付边界是：

```
笔迹采集 → 特征提取 → 模型推理 → 结果展示
```

### B：房树人、沙盘与Agent负责人

负责两个多模态模块的完整纵向链路：

- 房树人上传、绘制和结构化问卷页面。
- 沙盘元素库和拖拽画布。
- 沙盘几何特征提取。
- 房树人视觉观察。
- Agent Prompt、RAG和任务流。
- 房树人、沙盘分析结果展示。
- 两个模块的AI评测和安全测试。

交付边界是：

```
房树人/沙盘输入 → 特征处理 → Agent分析 → 结果展示
```

如果工作量过大，应优先完成沙盘，房树人采用“图片上传 + 结构化问卷”的轻量方案。

### C：公共基础与苍穹负责人

C不再负责所有业务页面，只负责公共能力和最终集成：

- 登录、首页、导航、个人中心等公共页面。
- Java统一网关和公共DTO。
- PostgreSQL公共数据模型。
- 用户、权限、审计、任务状态和文件管理。
- AI调用的超时、重试、幂等和日志。
- 本地Mock Agent环境。
- KWC公共组件规范。
- 苍穹领域模型、Java插件、Agent工具注册和部署。
- 最终端到端集成、安装包及演示环境。

交付边界是：

```
公共框架 + 数据底座 + 苍穹适配 + 系统集成
```

这样三个人都同时接触“页面、接口、逻辑和测试”，只是深度不同：

```
A：笔迹纵向模块
B：沙盘/房树人纵向模块
C：公共底座和平台横向模块
```

这种“纵向功能分工 + 横向公共底座”的方式更适合三人小组，也能避免：

- C成为所有模块的联调瓶颈。
- A、B的模型只停留在Notebook，无法真正接入产品。
- 某个成员不熟悉完整业务链路。
- 答辩时只有C能演示平台。

建议A和B至少完成各自模块的本地页面及API，C负责制定前端组件、接口和数据规范，并在苍穹环境开放后协助二人迁移。
